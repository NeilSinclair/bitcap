Codebase walkthrough — session notes

Read-only walkthrough, 8–9 September 2026. Notes taken while reading, to be condensed later. Nothing here is authoritative — it is what the code reads like from outside.

The register

Two different things in this repo are called “the register”.

1. The config files — what we track

This is the Register box in the pipeline diagram. It is nineteen YAML files and no code, because adding a lab, a person or a source has to be a config change (non-negotiable #6). The files are doing five different jobs, and they are much easier to read once you know which job each one has.

What reads what

Config on the left, the code that reads it in the middle, what gets written on the right. No config file imports another, and no module in the middle contains a threshold.

Things the diagram leaves out

  • posts_sources.yaml contains no handles. They come from people.yaml, so there is one list of who works where and no second copy to drift. What posts_sources adds is which handles to skip and why — a skip rather than a deletion, so that “we chose not to read this” doesn't look the same as “we don't know this person exists”.
  • companies.yaml also points at sources.yaml, because its lab_exposure edges are keyed on the lab. That's a third cross-file check; I left it off the picture to keep it readable.
  • Four different things read scoring.yaml — the scorer, the join (for route ceilings), the drift check and the transform. That's why the file carries so much comment: four stages have to agree about it.
  • The vocabularies are read twice, for different reasons. score_announcements.py pastes them into the prompt as {mechanisms}, {categories} and {practices}, and load_refs.py copies them into ref_* tables so joins can query them. Both read the same file, so the prompt and the database can't disagree about what a tag id means.
  • research/ reads the same config as app/. The one-off analysis scripts don't keep their own copy, so a calibration script's results still describe what actually runs.

2. The people tables — who works where

Papers and GitHub don't become insights. They become people and evidence, in three tables: Person, PersonIdentity and PersonEvidence (app/pipeline/register.py). The idea was to record who is at each lab and since when, so that a departure or a new stealth startup could be measured against it. app/people.py is the read side.

It was built but never trusted, and nothing downstream uses it. Move detection matches on names, and it reported people as changing labs when they hadn't — a byline appearing under two affiliations was enough to trigger it. The tables are populated and the harvesting works; the judgement on top of it was never good enough to ship, and not enough time went into fixing it. It feeds nothing in the digest, the scoring or the alerts. Read the rest of this section as the design of a leg that stopped short.

The merge rules are the part worth keeping, because they are deliberately cautious. That caution is why the failure showed up as visible bad output rather than a register that was quietly wrong.

Three merges the module refuses to make

  • The same name at two labs stays two people. Merging them would be a claim about someone's employment, made on the strength of a matching string.
  • A GitHub login and a paper byline are never merged. They are different kinds of identifier. Lookups go through PersonIdentity rather than the name (_person, register.py:125), so two legs producing an identical name at one lab still can't collide.
  • An affiliation the model read off a byline is recorded as model_asserted, never confirmed (register.py:294).

Details worth keeping

config/aliases.yaml is the only entity-resolution control an operator has, and code never writes it. A generator overwrote it once and destroyed ten confirmed merges: once an alias takes effect the duplicate spelling stops appearing, so regeneration correctly proposes nothing — and then writes that nothing over the file. Proposals now go to aliases_proposed.yaml instead.
  • Confirming an alias has to work retroactively. If both spellings were already loaded, _person resolves on the identity, finds the variant's own row, and never looks at the alias file — so nothing happens. _absorb (register.py:87) moves the loser's identities and evidence onto the winner and deletes it. Without that, the control does nothing.
  • Aliases apply at aggregation time only. Per-article bylines keep exactly what the page published, so any merge can be undone by editing config.
  • Per-load counts are measured before and after. They used to be whole-table totals reported as per-load figures, so the run log claimed 4,927 new people every night.
  • Everything upserts on a natural key. A repo not re-fetched this run keeps the row it had rather than being deleted as missing.
  • The GitHub canonical name is the login, not the commit name field, because the login is the identifier GitHub guarantees.
  • Bronze is written before the aggregate built from it, so a run that dies between the two keeps the commits it already paid to fetch.

Scoring

The LLM classifies and tags, with a verbatim quote on every tag. It never produces a number. config/scoring.yaml turns those tags into a score, and app/scoring.py — 82 lines — does the arithmetic. So every number can be argued line by line and changed without a deploy.

Two formulas over one extraction

investment  score = 100 × (event_weight/5) × max(magnitude × confidence)/3
ai team  ai_score = 100 × (action_weight/3) × max(impact × confidence)/3

The AI formula has no event weight, on purpose. event_weight ranks compute_commitment at 5 because clusters move semiconductor demand, which is worth nothing to an engineer deciding what to build with. The practice tag already says what kind of thing the item is. That's why the two audiences rank the same corpus differently rather than seeing one list in two colours.

The terms are multiplied, not added

An article with no mechanism tags has zero for the second term, so its whole score is zero. Every tag has to carry a quote, so an article can't score anything unless it quotes the document. An earlier version added the two terms instead, and articles scored 40 on their event label alone with no tags and no quotes.

There's a second reason not to add them. Event weight is already a guess at how strong the tags will be — compute_commitment is weighted 5 precisely because it tends to fire training_compute_up at high magnitude. Adding the two would count that twice.

A low-confidence tag counts as zero

confidence: low maps to 0.0, so a tag the model isn't sure about contributes nothing at all.

This changed on evidence. Someone hand-reviewed a 20-article run (docs/gold_review.md), and every tag they rejected as unsupported had already been marked low confidence by the model. The model was flagging them correctly; the scale was paying for them anyway. Two examples, both quoting marketing copy: inference_volume_up on OpenAI's $122bn raise, cited to “meet growing demand for ChatGPT, Codex, and enterprise AI”.

Making the change moved 34 items and dropped 5 to zero. All five were enterprise_partnership items scoring 4.4 whose only tags were low magnitude and low confidence. Nothing above 5 was affected; the largest fall was 66.7 to 50.0.

Other details

  • The model's is_signal flag is ignored (scoring.py:30). It used to be a hard veto. Then a stability check re-ran the classifier and found the flag flipping on 9% of items, including articles carrying maximum-strength quoted tags, which it zeroed. An article with no tags already scores zero through the arithmetic.
  • other is weighted 0, and how full it gets is a health check. It gives the classifier somewhere to put things that fit nothing else, instead of forcing them into a wrong category where the mistake would be invisible. In the v1 run it held 48 of 375 items — and alongside the office openings and student club forms sat both labs' confidential S-1 filings and three acquisitions, all scoring zero. That's what led to adding corporate_finance.
  • v1's problem was the vocabulary, not the arithmetic. The first US export control on a frontier model scored 20, because it was classified safety_policy (weight 1) rather than as something done to the lab. Adding regulatory_action and lab_capital_access fixed it under the same multiplied rule.
  • Each join route is capped at what it can prove. Four routes connect an article to a holding and they don't carry the same evidence — a mechanism tag is quoted on both sides, while named is just the company's name appearing in the text. All four write a strength into one column the digest sorts on, so a bare name match was landing at 1.0 next to a doubly-quoted mechanism. The caps: mechanism 1.0, category 0.6, lab_exposure 0.6, named 0.3.
  • Bands are labels on a score. They don't change it.

What filters the noise

Three separate things, at three stages, costing three different amounts.

1. Dedupe — config/dedupe.yaml

  • The exact pass runs first, and it fixes a correctness problem. One article can reach us at two URLs, and the classifier gave the two copies different event types. Since the event-type gate later on refuses to merge anything with mismatched types, it would refuse to merge two copies of one text. Running the exact pass first stops that. The differing types are classifier noise on identical input, not evidence the articles differ.
  • Tag overlap is not used to merge. Mechanism tags say what kind of event something is, not which event. Two unrelated partnership announcements score a perfect 1.0 on tag overlap.
  • Cosine similarity gets a band, not a threshold. In the labelled set, real duplicates run 0.70 to 0.966 and non-duplicates reach 0.79 — so wherever you draw a single line, you get errors. Instead: 0.80 and above merges, below 0.70 stays separate, and the gap between goes to a model. That gap is the only part that costs money.
  • The two edges are set differently. A wrong merge deletes an article from the product. A missed merge leaves a duplicate row the reader can see and ignore. So the top edge is placed to avoid wrong merges and the bottom edge to avoid missed ones, rather than both at some blended optimum that treats the two as equally bad.
  • What gets embedded is the title plus the classifier's summary, never the body. Bodies carry site furniture — “OpenAI Research Products Business Developers Company Foundation Log in Try ChatGPT” opens two different Astra articles — which raises the similarity between any two pages from one lab regardless of what they say.

Two ways the calibration nearly went wrong

  • The first labelling pass read a file sorted by cosine. The number was hidden but the ordering wasn't, which is the same information one step removed. Shuffling the file changed two of 82 labels — and they were the top two negatives, which is exactly where the upper edge sits.
  • Prompt v2 contains seven of the 20 blind-check pairs as worked examples, with the answers. So the 0.90 first written into the config was a score on its own training data. Out of sample it scores 12/13, the same as v1, and it introduces one wrong merge v1 didn't make. A fresh blind check on unseen pairs is still outstanding.

The whole pass, drawn

Three passes merge rows and the fourth only links them. The order matters: exact match first, then release trains, then the cosine pass — and only the middle of the cosine band costs anything.

The short version

A release never reaches the expensive path. Pass 2 handles it, and that's all the grouping it gets.

What “normalised title” means

One line, and less clever than it sounds:

re.sub(r"[^a-z0-9]+", " ", (title or "").lower()).strip()

Lowercase, then every run of non-alphanumeric characters becomes a single space, then trim. No stemming, no stopwords, no fuzzy matching. It absorbs curly versus straight quotes, em-dash versus hyphen, trailing punctuation and casing — the ways one publisher's CMS and a forum mirror render the same headline differently. It's one third of the bucket key (lab, published_on, normalised_title), and a bucket holding more than one row is one article at two URLs.

It deliberately doesn't do fuzzy matching. “Introducing GPT-6 Astra” and “Introducing GPT-6 Astra: A New Generation” normalise to different strings and don't match here; they fall through to the cosine path. This gate merges on no other evidence at all, so it only catches titles that are identical once punctuation is gone.

What has to be true for a link (pass 4)

A release can link to several articles. But four things have to hold, not just the model name:

  1. The model identifier matches, with both sides stemmed. Stemming only one side lost the case the feature exists for. The identifier pattern doesn't span a space, so the launch post “GPT-6 Astra: A new generation of intelligence” yields only gpt-6, while the release body's “GPT-6-Astra” yields only gpt-6-astra. Those never intersect, so the only announcements that linked were the ones that happened to hyphenate.
  2. Same lab.
  3. Within 14 days.
  4. The article's event_type is a model release — frontier_model_release, incremental_model_release or open_weights.
Condition 4 is what does the work. Once both sides are stemmed, gpt-6 reaches every Astra-adjacent post. On identifiers alone the launch post and “Legora reviewed 41 documents in minutes with GPT-6 Astra” are identical — both yield exactly {gpt-6} — so no threshold over identifiers could separate them. Their event types can, and that's a field the pipeline already trusts to separate things in pass 3.
  • One edge per pair, on the longest shared identifier. Writing one edge per shared key produced gpt-6 and gpt-6-astra as two rows for one fact, and the card then said the same thing twice.
  • sorted before max matters. max over a set breaks ties in iteration order, which follows string hash randomisation, so a pair sharing two same-length identifiers stored a different evidence string on each process. A table rebuilt from scratch has to come out the same every time.
  • safety_policy is left off the list, even though “Safety overview: GPT-6 Astra” is genuinely about Astra. It reports a crossed Preparedness threshold the launch post never mentions, so pointing the release at it would say the model was announced there.

2. The digest cut — config/digest.yaml

The dashboard shows every classified article. The digest picks a handful and says the rest aren't worth reading. Every threshold below is that choice written as a number, and each edition records how many items it left out.

  • Investment: an item gets in if it has a connection to a holding at strength 0.5 or above. That's the normal route, and most items in the digest arrive that way. Failing that, it still gets in if its band is high, even with no connection at all — a lab-level shift that hasn't yet touched anything in the book is the early signal worth catching, and requiring a connection would filter it out.
  • AI: the item needs a practice tagged adopt or investigate, and band high. watch means “nothing to do yet”, so including it would fill the digest with items whose own tag says to ignore them.
  • Connections below 0.5 aren't thrown away — they're still shown on the card, they just aren't what got the item in.

The 16-item cap does nothing right now

Both audiences cap at 16 items. The cap never actually kicks in, because the quality rules admit far fewer than that anyway — the investment rule lets 2 items through out of 58 considered. You could set the cap to 8 or to 1000 and get the same digest. It was raised from 8 so the two audiences wouldn't differ for no reason.

Two windows, deliberately different numbers

window_hours is 24. That's the published edition: quantised to a fixed grid, one per day, stored permanently. preview_window_hours is 168 — the last seven days, ending now. That's what you see when you open the page, and it's rebuilt on every load and never stored.

They used to share one value, which meant the archive of editions a reader could browse was frozen at whatever the number happened to be when they were published. An archive that records “the labs published nothing on the 14th” is doing its job. A landing page that's empty half the time teaches people to stop opening it. Those are different requirements, so they get different numbers.

The file also says its own measurements are stale: the window table was taken before papers, releases and posts joined the digest, and before the AI band moved to high. It tells you to read it as the shape of the trade rather than as current figures.

3. Drift — app/pipeline/drift.py

  • It re-runs the classifier on a fixed set of articles every run and compares the tags. It calls the uncached path deliberately: reading through the result cache would return the stored answer every time and report perfect agreement forever, which is the one failure that looks exactly like success. So this check always costs money.
  • The provider's prompt cache is left on. One call runs on its own first to create the cache entry, then the rest fan out. A cold parallel start would bill every request as a cache write at 1.25× instead of a read at 0.10×.
  • The sample is a fixed named list, not a random draw, so a change between runs is the classifier moving rather than the sample moving.
  • It started at six articles, and that was too few. Six articles carry ten reference tags, so one tag gained or lost moves micro-F1 by about 0.05 — and the alarm floor was 0.80. The first run to breach it scored 0.750, which is either real degradation or three tags of noise, and six items can't tell you which. It's now all 20 gold articles, about $0.75 a run.
  • The headline number is mechanism micro-F1, not a blend. Under the scoring rule an article with no mechanism tag scores zero, so agreeing about mechanism tags is the same thing as agreeing about the score.

One document, two numbers, and what reaches the screen

One model call at the top. Everything below it is arithmetic over the tags that call produced.

The two lanes are two renderers over the same extraction. That's why they can rank the same corpus differently without being two systems.

The join in detail — app/connect.py

It answers one question per article: which holdings does this touch, and how strongly. It runs after scoring, writes the connections table, and uses no LLM — the classifier already did its part by tagging the article.

Both sides carry the same three fields. An article's mechanism tag has magnitude, confidence and sign. So does a holding's mechanism edge in companies.yaml. A connection exists when the two name the same mechanism id.

Each side is turned into a number between 0 and 1 by the same function, reading the same maps from scoring.yaml:

weight = (magnitude × confidence) / 3
magnitude:  high 3, medium 2, low 1
confidence: high 1.0, medium 0.5, low 0.0

High/high is 1.0, medium/medium is 0.33, and anything low-confidence is 0.

RouteStrengthWhy that shape
mechanismarticle weight × holding weight × 1.0Both sides quoted, signed and sized.
categoryarticle confidence × 0.6No magnitude — belonging to a category has no size.
lab_exposureholding weight × 0.6Holding side only; the classifier has no lab-sentiment axis.
namedflat 0.3Nothing to weigh. A string matched.

Worked example: an article tags memory_intensity_up high/high/positive; Micron's edge is high/high/positive. Strength = 1.0 × 1.0 × 1.0 = 1.00, direction positive. Drop the article tag to medium/medium and it becomes 0.33.

Directions compose like signs: positive × positive = positive, positive × negative = negative, and mixed on either side wins, because a guessed direction would be shown as evidence.

Four guards

  • A zero-strength connection is never written. Low confidence on either side removes the row.
  • lab_exposure only fires when the article scored above zero. That edge fires on the publisher rather than on what was published — ungated, a Brazil office opening reached Amazon.
  • One row per (holding, route, via), strongest kept. The classifier sometimes tags one mechanism twice with different quotes.
  • Name matching has floors. Legal suffixes stripped (“Micron Technology, Inc.” → “Micron”), minimum 4 characters, and tickers must be 3+ characters and uppercase-exact, so MU and ON can't fire in ordinary prose.

There are three lab_exposure edges in the whole config, and one of them is dead:

Strength is 0.60 and the arrow is always neutral, because direction is hardcoded to mixed. 0.60 clears the digest's 0.5 threshold, so an Anthropic article with no other connection can reach the investment digest on this route alone.

Dashboard and digest read the same rows

/api/items attaches every connection an article has — no route filter, no strength filter — so the dashboard shows all four routes, including named at 0.30 and anything below the digest's threshold. Its only filter is on date (window_start(), from pipeline.yaml). The digest is a filtered subset of the same data.

One article, traced all the way through

A real example from the dashboard: a Meta announcement, scoring 40.0, reaching two holdings.

Two numbers come out of one set of tags. The score says how much this document matters; the strength says how much it matters to a particular holding. Neither is produced by the model.

An open question about the company side. On the article side, magnitude and confidence measure genuinely different things — a document can state a small effect plainly, or hint at a large one. On the company side that separation is weaker: it is hard to say what “medium confidence that the impact is high” means about a standing relationship between a mechanism and a company. Magnitude alone might carry it. Noted, not changed.

Parts of that flow worth saying in words

  • The join is deterministic and carries its quotes. Four routes, each storing its provenance on the row. lab_exposure only fires when the article scores above zero, because the edge fires on the publisher rather than on what was published — ungated, it connected a Brazil office opening to Amazon.
  • Category and mechanism can disagree, and the code picks a side. A category tag is a claim about a group of companies; a mechanism edge is evidence about one company. OpenAI shipping its own accelerator reads positive for the accelerator category and negative for NVIDIA specifically. _drop_contradicted_category_rows removes the group row where that company's own mechanism row points the other way, since showing both confuses rather than informs. Only strict opposites count.
  • The reader never sees a bare route name. _connection_label in api/queries.py turns the row into what it actually matched — the mechanism's label, the category's label, “Lab relationship — …”, or Named in article — "…". The word “mechanism” on its own says nothing.
  • The note prefers the holding-side why over the article's own reason, and falls back only when there isn't one. Category rows never carry a holding-side why, because membership has no argument attached to it.
  • Folded duplicate groups rank on the axis being displayed. event_type is multiplied into the investment score and absent from the AI score, so the member ranking highest overall can score zero on the axis you're looking at.
  • Published digests are stored and never recomputed. A digest records what the product said on a given day. Rebuilding an old one against a re-scored corpus would show today's opinions under last week's date.

Text provenance — knowing what was actually read

Sources degrade unevenly. openai.com sits behind Cloudflare and returns 403 to every fetcher tried — plain curl, a browser user agent, a full browser header set, Googlebot — but serves XML, so discovery runs on RSS and gets a two-line editorial summary. Other labs give up the whole page.

A score computed from two lines and a score computed from a full article are not comparable. Nothing downstream can tell them apart unless the item says so. That's what text_source is for, and it's used in two places:

  • In the prompt. v9 has a section telling the model what it's holding and what to do about it: full_text normal confidence · rss_summary cap confidence at medium, you're reading an abstract · full_text_archived treat as the real article, but site furniture may have survived the extraction so never quote from it · model_spec first-party and canonical, and the absence of benchmarks is a property of the format, not weak evidence.
  • On the rendered item, so a reader can see that a low score came from a thin source rather than a thin event.
The fallback enriches the existing row. It never creates a new one. enrich_wayback takes the articles RSS already found (text_source == "rss_summary"), fetches the archived text, and upgrades them in place. The article keeps its canonical openai.com URL; the archive URL is stored as archive_snapshot metadata. Since raw_articles is keyed on url, duplicates are impossible by construction rather than something dedupe has to catch later.

Three things learned the hard way

  • The enrichment runs inside the fetch, not after it. The fetch rewrites the register from scratch, so a recovery pass that runs afterwards lasts exactly until the next fetch. It was run afterwards once, and 141 recovered articles reverted to summaries overnight with nothing reporting it.
  • A snapshot shorter than the summary is refused. That's a redirect stub or an error page, never an improvement, and both are common in archives.
  • What couldn't be recovered is reported as an unresolved row per item, rather than passing quietly. A source stuck on summaries is exactly the degradation this field exists to make visible.

Measured 2026-09-05: 131 of 149 OpenAI articles are archived, and the recovered text runs 12× to 98× the RSS summary. The 18 that aren't are mostly customer stories and academy pages — with one exception worth knowing about, the GPT-6 Astra safety overview, which is substantive and has never been crawled.

The open edge: an article settles once it's classified, which happens in the firing that discovers it, so enrichment gets one attempt. Anything the archive hasn't crawled inside that window keeps its summary permanently.

To fix

Raised while reading, not actioned. Each needs a decision before any code changes.

1. The dashboard can't sort by impact on a holding

The dashboard offers two sorts, score and date, and score means the article score for the selected audience (frontend/app/page.js:166). Connection strength never enters the ordering across cards — only within one card, where api/queries.py already returns connections strength-descending.

The investment digest does it the other way round: selection ranks on connection strength first, then article score (app/digest.py, “TWO SORTS, AND THE ORDER OF THEM IS THE POINT”). So the two surfaces rank the same corpus differently.

This matters most with the holding filter on. Pick NVIDIA and you get every article connected to NVIDIA, ordered by how important the article is in general rather than by how hard it hits NVIDIA. That is the moment a reader is asking the second question, and the answer isn't available.

Fix: add a third sort option — impact — ranking on the article's strongest connection, or on the connection to the filtered holding when one is selected. The data is already in the payload, so this is frontend-only.

2. min_strength is a misleading name

min_strength: 0.5 sits under investment: in digest.yaml and filters connection strength, which runs 0–1. The article score runs 0–100 and is filtered separately by always_band. Two scales, two different things, one name that doesn't say which.

It has already caused a mistake once, recorded in digest.yaml: the AI cut was asked for as “scores above 0.5”, but there is no 0–1 score on that axis — ai_score is 0–100, and the 0.5 in the investment block is a connection strength the AI rule doesn't use at all.

Fix: rename to min_connection_strength.

3. Should the article score be its highest impact on a holding?

The current article score is event_weight × strongest tag and knows nothing about the portfolio. An alternative: score the article on its strongest connection instead, which would answer the question the fund actually asks and would let event_type drop out of scoring entirely.

Four things that would cost:

  • The early signal disappears. An article about a lab shift that doesn't yet touch anything in the book would score 0. That is precisely what always_band: high exists to catch — the item that arrives before the market has priced it. This change deletes it by construction rather than by choice.
  • The score becomes a function of the portfolio. The book is 26 positions of one fund on one date. After a rebalance every article's score moves, and last month's scores stop being comparable with this month's.
  • A missing edge looks like unimportance. A connection only exists where someone hand-wrote an edge in companies.yaml. An article about something real but unmapped scores 0, and that can't be told apart from an article about nothing.
  • The AI axis still needs its own score, because it has no holdings. So this doesn't collapse to one number — it gives two differently-shaped ones.

Already partly done: the investment digest ranks on connection strength before article score, so the fund's ordering exists there without making the score itself portfolio-dependent. Item 1 above would extend the same idea to the dashboard.

4. The last layer should be a serving table, not fourteen joins

/api/items reads fourteen tables, substitutes ids for labels, and ships the whole corpus so the browser can filter it. That work is identical on every request and depends on nothing about the request. It is precomputation pretending to be a query.

The dashboard and the digest are the same object with different filters. Build one denormalised table that is what the reader receives, and have both read it:

cards
  article_id, audience, published_on, score, band,
  top_connection_isin, top_strength,   -- precomputed: what got this in
  payload                              -- summary, tags with quotes, connections
                                       --   with labels, group, related links

Three things follow:

  • To-fix item 1 disappears. Sorting by impact on a holding needs top_strength stored, not computed in the browser.
  • The feed stops shipping everything. One response with the whole corpus works at 746 rows and breaks at 50,000.
  • Audience becomes a column instead of parallel score/ai_score fields that every consumer branches on. The two-renderer design lands in the schema rather than in if statements.

And store a published edition as a selection, not a copy. An edition has to record what was said on a date, but digests currently stores the rendered payload, which freezes everything — fix a mechanism label and the dashboard updates while old editions keep the old wording for ever. Store the decision and the numbers behind it, and render from current data:

digest_editions  id, audience, period_start, period_end, published_at, suppressed_count
digest_items     edition_id, article_id, rank, score_at_publish, strength_at_publish

The rule this gets you: the dashboard and the digest are one table with different filters, and the only thing worth storing separately is which rows went out and when.

5. Company-side confidence may be redundant

On the article side, magnitude and confidence measure different things: a document can state a small effect plainly, or hint at a large one. On the company side that separation is weaker — it is hard to say what “medium confidence that the impact is high” means about a standing relationship between a mechanism and a company. Magnitude alone might carry it.

Fix: decide whether the field earns its place. Dropping it changes every strength in the join, so it needs the gold set replayed before and after.
